# Battery 2: pre-registration

Frozen 2026-11-04, before any key is built or any model is asked. The design is `design/final-design.md` (merged by Claude Opus 5.5 from eight models' proposals and seven critiques; inputs in `design/`). This file records what the owner decided on top of it and wins where they differ.

## Owner's decisions (2026-11-04)

1. **The admission rule is frozen as designed** (final-design.md, section E). After the results, any threshold may be **raised, never lowered**, on any dimension, if the findings show the bar is affordable. A raised bar is recorded here with its reason before it is applied. Reason: what counts as "harmful" is hard to pin down in advance; tightening after seeing the data can only reject more, never rescue a model.
2. **Models under test run at their production setting**: `reasoning.effort = "max"` (DeepSeek, Kimi, GLM, MiMo Flash), no reasoning parameter for MiMo 2.6 Pro, non-Anthropic models via `:exacto` endpoints. This replaces the design's "minimal reasoning, 250-token cap"; the answer cap is raised so reasoning does not crowd out the answer.
3. **Keys are built by tools**, run by a headless agent on Claude through OpenRouter with `provider.only = ["anthropic"]` (the owner's Claude API key), with DeepSeek's search and fetch, and DeepSeek Flash 1017 for bulk extraction. This session (Claude Code) only writes the harness and reviews outputs.
4. **The owner adjudicates up to 20 items**, blind to model identity, each shown its saved evidence and a drafted verdict. Items are prepared so that adjudication needs at most an ordinary web search, never recall of hard-to-find details.

## Rule validation before the run

The simulation of section E ("Rule validation") runs before any model is asked; its output is committed here. If a required outcome fails, thresholds are revised and recorded before the run, never after.

4. **2026-11-09, before any further item is built (the owner's decision, 2026-11-09): the two records of an item reach the pipeline through different fetch APIs.**
   - **The reason.** Both records used to come through one fetch API (DeepSeek's), which returns its own conversion of the page, not the page. Whether that conversion involves a model is UNRESOLVED (DeepSeek's documentation host is outside this session's network). If one converter alters a field the same way on both pages, the code comparison agrees with itself and the error passes. Two converters from different companies are unlikely to share such an error.
   - **The rule.** In the seeded intake of deviations 2-3, record A (the CNKI article page) is fetched through DeepSeek's fetch API and record B (the institute's table of contents) through Moonshot's. `stage_b` reads the fetcher from each record's saved snapshot and drops the item (`same_fetcher`) when they are the same. The search intake (both records through DeepSeek) is not covered: it has produced no accepted item, and an intake for other sources follows this rule or records its own deviation before it builds an item.
   - **Why this way round.** Probed 2026-11-09: for `cnki.com.cn/Article/CJFDTotal-ZYJY201602002.htm`, Moonshot returned 801 characters without the 相似文献 block that `cnki_entry` reads, and DeepSeek returned the page with it; for the `iwr.cass.cn` 2019 table of contents, Moonshot returned the entries, and DeepSeek returned HTTP 502 on that one try (it had opened the same page for run 2, so this is one observation, not a property of the fetcher).
   - **What was observed about the converters** (not a proof): a plain-text page fetched twice through DeepSeek was byte-identical, and differed from a local copy of the same text only by 13 lines in which an angle-bracket span (`<https://…>`, `<year>`) had been removed; nothing was reworded (one page). On 20 items re-fetched through Moonshot on 2026-11-09, title and authors matched on 19 and the 20th page came back without its author line.
   - **Items whose record B was saved before this deviation**, accepted or still in progress, are selected by their snapshots, not by host: every item whose two snapshots name one fetcher. On the next run of its work directory, `stage_b` (`reread_record_b`) reads record B again through Moonshot with the same `toc_entry` and compares title, author, venue and year with the stored entry, by the comparisons `stage_d` uses. Fixed now, before that run: an item whose entry is absent from the page, ambiguous or different is dropped with its reason, and none is repaired; an item whose entry is equal keeps going with the Moonshot snapshot as record B (its key, clues and verdict were made on the earlier snapshot, which the record names); an item whose page Moonshot does not open, or returns in a form `toc_entry` cannot read (no header, an author line it cannot split), is held: marked `not_rechecked`, stopped at that stage, left out of every output file and counted in the report. A page not read is not evidence about the item, so it neither drops nor passes. A failed fetch is cached, so trying again means deleting that snapshot, and the run notes say so when it is done.
   - **Unchanged.** Fields are compared in code and any mismatch drops the item. The search API (recoverability, identifiability, footprint counts) still has one provider; a second search channel is not part of this deviation (Gap).

5. **2026-11-15, before any dropped item is read again (the owner's decision, 2026-11-15): an item dropped because of how a page was converted, and not because its two records disagree, is read again once; code selects it and code compares it, by the unchanged comparisons.**
   - **The reason.** The comparison exists to keep out a key whose two records disagree or whose source was invented. An audit of the dropped items on 2026-11-14 (after the owner asked whether code can drop wrongly) found that 22 of the 37 `field_mismatch:author` drops hold the same characters in the same order in both author fields; they differ only in where one name ends and the next begins (in the pattern `甲乙；丙丁戊` against `甲乙丙丁戊`; made-up names, since a real pair could end up in the answer key). The re-read of deviation 4 also dropped one accepted item because the Moonshot conversion broke its title over two lines. In both cases the records agree and the reading failed, which is outside what the comparison is for. A drop used to be final; this deviation lifts that for the two cases below and for nothing else.
   - **Which items (selected in code, `layout_drop`).** Only items of the seeded intake (those with a table-of-contents address for record B). (a) A `field_mismatch:author` drop whose two author strings hold the same non-empty sequence of CJK characters; characters outside CJK are ignored for this selection, which decides only who is read again, not who passes. (b) A `toc_entry_absent` drop made by the re-read of deviation 4. Counted before the run: 22 of kind (a) across the four work directories (two of them are the same article, seeded in runs 1 and 3), 1 of kind (b). The other 15 author mismatches and the 10 first-pass `toc_entry_absent` drops are not selected.
   - **What happens to them (`--reopen-layout-drops`, with `--stage b` only).** An item is reopened once. Kind (a): the stored record B is set aside and record B is read again through Moonshot by the same `toc_entry` (the fetcher deviation 4 assigns to record B; where a Moonshot copy of the page was saved on 2026-11-09, that copy is read and no new request is made). `stage_d` then compares the two records with no change to any comparison. Kind (b): the item still has its key, clues and verdict, so it is held (in no output) from the moment it is reopened until `reread_record_b` has run again. For these items only, `toc_entry` reads a title that the converter broke over two lines as one, when the line before holds no entry and the two lines joined equal record A's title after `norm`. Every other reading uses `toc_entry` as before.
   - **Outcomes, fixed now.** Kind (a), equal by `stage_d`: the item continues through every later stage as any item does (recoverability, clues, pre-screen, verification) and can still be dropped there. Kind (a), anything else (still different, entry absent or ambiguous, page not opened or not readable): it stays dropped with the new reason recorded, and it is not repaired. Still different is the expected outcome wherever record A's own catalogue line cuts the names at different places from record B (seen on 2026-11-14 for three articles, in the pattern `甲乙；丙丁；戊己` against `甲乙丙；丁戊己`), and wherever Moonshot also returns the names run together (one item of the 22 already had record B through Moonshot). Kind (b), the new reading equal to the stored entry by the comparisons of `stage_d` (the stored entry is the one that passed `stage_d` against record A): the item returns to the accepted set on its earlier key, clues and verdict, with the Moonshot copy as record B; no later stage runs again. Kind (b), entry absent, ambiguous or different: dropped again, for good. Kind (b), page not opened or not readable: held, as deviation 4 holds such an item. How many come back is not known in advance and is reported as counted, whatever the number.
   - **Not checked before writing this:** whether Moonshot keeps the names apart on these pages. The Moonshot copies of the tables of contents were saved on 2026-11-09 and were not read for this purpose before this text was committed.
   - **What this does not do.** No comparison in `stage_d` or `reread_record_b` is changed, no name is split or joined by code or by hand, and no model takes part. The two-line title reading is the one place where what counts as record B's title is wider than before, and it applies to the reopened kind (b) items only. The 25 drops not selected stay dropped.
